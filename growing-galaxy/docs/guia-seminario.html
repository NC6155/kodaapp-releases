Preparar la presentación

La aplicación usa Astro para renderizar páginas y ejecutar las rutas de servidor. Node consulta PostgreSQL mediante el paquete pg. Esta entrega incorpora Caddy como proxy inverso y mantiene las mismas URL de las pantallas y las API.

Navegador → HTTPS → Caddy → HTTP local → Astro / Node → PostgreSQL

El servidor también usa SMTP para correo y Blob Storage para fotografías. El proxy publica la aplicación en el puerto 8443. El backend escucha en 127.0.0.1, puerto 4321.

Inicio en este equipo

Set-Location 'C:\Users\matia\Documents\kodaapp\pagina-tesis\growing-galaxy'
npm.cmd run presentar

Abre https://localhost:8443. Mantén la terminal abierta durante la demo. Para terminar, pulsa Ctrl+C. Caddy genera un certificado local. Si el navegador pide confianza, la raíz propia de esta demo está en la carpeta .koda-local después del primer inicio. Comprueba su ubicación con Get-ChildItem .koda-local -Recurse -Filter root.crt. Puedes importar esa raíz en el almacén de confianza de tu usuario para este equipo.

Reproducir la instalación

En este equipo quedaron aplicadas la migración y la compilación. Para preparar otra instalación con las mismas dependencias, Node compatible con ejecución directa de TypeScript (probado con Node 26), PostgreSQL y Caddy, crea el esquema base de ../bdkodapp.txt, configura .env y ejecuta:

npm.cmd run migrar
npm.cmd run demo
npm.cmd run build
npm.cmd run presentar

La cuenta PostgreSQL que prepara la demo necesita permiso de crear una base local. La semilla se puede repetir y conserva los cambios hechos durante el seminario. Fuera de la demo, la administración se asigna a una cuenta existente insertando su ID en administradores.usuario_id desde una sesión de mantenimiento autorizada. El registro web solo ofrece adoptante y organización.

Decisiones de datos y negocio

Qué cambia al aprobar

La solicitud comienza pendiente. Antes de aprobar, el servidor bloquea la ficha de la mascota, verifica que pertenece a la organización y vuelve a consultar el rol, la suspensión y los cupos del adoptante. La aprobación, la marca «adoptada» y el rechazo de las solicitudes pendientes competidoras se guardan en la misma transacción.

El máximo inicial es 3 adopciones simultáneas. Una postulación pendiente consume cero cupos. Una aprobada con tenencia abierta consume uno. Al registrar el cierre, queda la fecha, se libera el cupo y la mascota pasa a «reservada». La organización puede volver a publicarla desde la edición. Al reducir el máximo se conservan las adopciones existentes y se bloquean nuevas aprobaciones cuando corresponde.

Una denuncia abre una revisión humana. La suspensión se aplica a la cuenta y revoca sus sesiones. Un reporte por sí solo no prueba maltrato. La plataforma no consulta registros externos de antecedentes. La regla histórica de una postulación por pareja mascota–adoptante sigue vigente incluso después del cierre.

Cómo entra un registro crudo

{"referencia":"seminario-01","nombre":" Mora ","tipo":" GATO ","personalidad":"tranquilo","salud":"vacunacion_al_dia"}

El importador convierte « Mora » en «Mora» y « GATO » en «gato». Busca la organización por ID, resuelve los códigos contra el catálogo y guarda texto y código en la ficha. Una línea inválida revierte el lote completo. Repetir la referencia en la misma organización omite esa fila y conserva la ficha existente. La edición posterior corresponde al módulo de gestión.

node --env-file=.env --env-file=.env.demo.local scripts/importar.mjs demo/mascotas.jsonl ID_DEL_REFUGIO

Sustituye ID_DEL_REFUGIO por el ID visible en Administración → Cuentas. El archivo incluye un gato y un perro ficticios.

Serialización, consultas e historial

leerPostulacion acepta un cuerpo JSON, valida identificador, vivienda, teléfono, motivación y confirmación, y devuelve únicamente los campos que persiste la ruta. El serializador de fotos construye la URL desde la fila seleccionada. El catálogo ya traía fotos en un lote adicional. Ahora trae la referencia en el mismo SELECT. La descarga de los bytes sigue siendo una petición HTTP por imagen.

Los paneles de solicitudes reúnen adoptante, mascota y organización con JOIN. La vista común de mascotas postulables excluye tenencias abiertas y organizaciones suspendidas. El índice parcial por mascota protege la unicidad y el índice por adoptante ayuda al conteo del cupo. Las fechas de solicitud, resolución y fin de tenencia quedan en PostgreSQL. La clave foránea impide borrar una ficha con solicitudes asociadas.

Evidencia y alcance de la validación

ComprobaciónResultado observable
Transporte y accesoUna petición HTTPS atraviesa Caddy y llega a Astro. El login establece cookie Secure y HttpOnly. Un adoptante recibe 403 en administración.
Validación en servidorID de mascota de tipo incorrecto → 400. Origen diferente → 403. Solicitud duplicada → 409. El texto ordinario con apóstrofo se conserva al leerlo de PostgreSQL.
Dos organizaciones y un cupoAmbas intentan aprobar mascotas distintas para el mismo adoptante. Una aprobación devuelve 200 y la otra 409. El cierre libera el cupo. Un segundo cierre devuelve 409.
ModeraciónUn participante envía un reporte. Administración lo revisa, suspende y reactiva. La sesión previa caduca y aprobar al adoptante suspendido devuelve 403.
IntegridadBorrar una mascota con solicitudes devuelve 409. Importar dos fichas inserta dos filas. Reintentar inserta cero. Una línea inválida deja cero filas de ese lote.
Prueba previa del proyectoEl script existente comprueba ejemplos de RUT, incluido el dígito K, y el desbloqueo del botón de reenvío a los 60 segundos.
Plan del catálogoEXPLAIN (ANALYZE, BUFFERS) en la semilla de cinco mascotas devolvió cuatro disponibles. El plan observado usó el índice de estado y el índice parcial de tenencias. Esta muestra sirve para explicar el plan. Faltan mediciones de carga con volumen representativo.

Guion para la comisión

  1. Presentar la arquitectura. Mostrar Caddyfile, la ruta de Astro y el pool de PostgreSQL. Abrir el catálogo público.
  2. Entrar como adoptante. Mostrar las preferencias y comparar una ficha con su compatibilidad. Abrir Mis postulaciones y explicar la diferencia entre solicitud pendiente y cupo utilizado.
  3. Entrar como refugio. Aprobar la solicitud pendiente de Olmo. Mostrar el estado de la ficha, la desaparición del catálogo y el cambio visible al adoptante.
  4. Revisar un incidente. Desde una solicitud, enviar un reporte de demostración. Entrar como administrador, revisar el reporte, suspender con motivo y mostrar el historial. Reactivar para continuar.
  5. Mostrar el límite. Explicar la prueba de concurrencia y el resultado 200/409. Cerrar la tenencia desde Gestión → Postulaciones y mostrar la fecha histórica.
  6. Mostrar los datos. Importar los dos registros JSONL en la base demo. Repetir para mostrar la deduplicación. Volver al catálogo.

Límites que conviene declarar

El historial médico es un campo descriptivo clasificado por salud. No hay una cronología de consultas veterinarias ni verificación de identidad externa. La suspensión requiere una decisión de administración. La clasificación de Match depende de los datos disponibles. Los listados de mascotas y el cálculo de Match aún cargan el conjunto completo. El panel administrativo muestra hasta 50 cuentas por búsqueda, 50 reportes pendientes y las 50 acciones más recientes.

El proxy entregado se configuró para el equipo local. Un despliegue público requiere su propio dominio y certificados, configurar KODA_PUBLIC_ORIGIN antes de compilar y ajustar KODA_SITE y KODA_BIND para el servidor. El build actual avisa de una referencia CSS previa a /decoraciones.svg que falta en public.
